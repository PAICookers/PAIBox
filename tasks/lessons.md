# Lessons

- When creating a new working branch for this project, use a simple task-style prefix such as `feat-...` or `bugfix-...` rather than nested names like `codex/...`.
- When the user has not explicitly asked for a commit, keep code changes uncommitted and ask before creating any git commit, even on an isolated working branch.
- When a helper is used to narrow graph-node unions inside compile passes, annotate it with a broad input type and `TypeGuard[...]` so static typing matches the control-flow narrowing.
- When the user asks to compile several modules "as one network", do not split them into separate per-module compile helpers; first preserve the requested graph boundary, I/O arity, and combined compile path.
- When the user provides a network summary log with real feature-map sizes, use those logged shapes for compilation defaults instead of placeholder reduced sample shapes.
- When a type is specific to one compile pass family (for example AvgPool deployment metadata), keep it in that pipeline subpackage by default and break cycles with typing-only references or generic annotation storage rather than promoting it into core IR public API.
- When consolidating test helpers, do not split out a separately named wrapper that has only one internal call site and adds no semantic distinction; keep the helper surface minimal and inline trivial one-step wrappers.
- When the user asks for the final compile implementation only, do not add a parallel `torch_to_paiir()` inspection path; keep diagnostics and tests on the single `compile_to_paiir()` result unless stage-by-stage comparison is explicitly requested.
- When the user only needs the current environment/version confirmed for a compile task, do not block the task on `poetry lock`; verify the active runtime version first and proceed unless the user explicitly asks to refresh lockfiles.
- When the user asks to revert a targeted change, revert only that scoped change and keep unrelated compatibility fixes that solve separate breakages.
- When the user asks for analysis or benchmarking first, do not preemptively change production source; add a test-only or benchmark-only harness first and use its results to justify any later code change.
- When a helper function's scope changes materially, rename it to match the new behavior instead of keeping a legacy name that implies the old flow.
- When a compile helper says its default shapes come from a network summary log, verify those defaults against the actual logged in-network tensor shapes before relying on them for backend compilation.
- When a user-facing test script starts accumulating trial-specific wrappers, collapse it back to a small number of direct entry functions and keep exploratory variants behind parameters rather than separate top-level flows.
- When a user explicitly asks to avoid parameterization in a test helper, move the tunable value to a single top-level constant instead of keeping it in the function signature.
- When a user asks for the simplest possible test helper, prefer fixed test constants and direct layer construction over generic scaling helpers.
- When the user says a test only needs to validate shape suitability and compile completion, do not keep real-weight copying or quantization in that path.
- When a real-weight test intentionally omits a BatchNorm layer from the compiled graph, fuse that BN into the preceding Conv first so the compiled path matches eval-time inference semantics.
- When simplifying `tests/user` around a new customer-model scope, keep explicitly protected generic regression tests such as `dualcnn`; only remove legacy tests that are truly tied to obsolete customer artifacts.
- When code already narrows a module to `nn.AvgPool1d` / `nn.AvgPool2d` via `isinstance`, access attributes like `count_include_pad` and `padding` directly instead of adding redundant defensive `getattr(..., default)` calls.
- When the user explicitly excludes directories such as `backendv2/**` or `tests/backendv2/**`, keep both implementation and verification entirely outside those directories rather than adding “just one exploratory test”.
- When two existing helper functions already express adjacent semantics clearly (for example real pool window size vs effective AvgPool divisor), prefer direct helper calls over introducing a one-off wrapper dataclass just to return both together.
- When generated `.log` artifacts may be shared externally, avoid absolute filesystem paths in the file contents; prefer repository-relative or sibling-relative paths.
- When an object-namespace cache keys names by `id(obj)`, watch for Python object-id reuse leaking old class prefixes into new node names; prefer weak object-key mappings over raw id-based caching.
- When tightening shape metadata types or reshape canonicalization behavior in PAIIR, do not stop at focused helper tests; run the broader `tests/paiir` suite because multiple compile/simulation tests may encode the old graph-shape assumption.
- When an optimization only becomes viable by excluding common project modules such as native neurons, LUT activations, or custom registered neuron types, do not pursue it; prefer hotspots that improve the normal compile path without operator-specific exclusion lists.
- When `InputNode/OutputNode.shape` is narrowed to `torch.Size`, update explicit test/examples call sites to pass `torch.Size(...)` rather than relying on tuple compatibility.
- When the user asks for PR copy, default to a concise team-style daily PR version first; expand to a fuller GitHub PR body only if the user asks for more detail.
- When the user broadens a naming-cleanup request from one build knob to all eval-board/default-SDK identifiers, stop and do a full impact review of the primary source tree before proposing or making any rename edits.
- When a PAIRV application has a hardware-imposed download-mode requirement, encode that constraint directly in the application Makefile and mirror it in root help/docs instead of relying on tribal knowledge.
- When the user removes build-facing files or sample applications from PAIRV, update the README and help text immediately so the documented active tree matches the filesystem exactly.
- When building customer-specific import/compile tooling for this repo, keep it under `tests/user/**` rather than `paibox/**`, and prefer explicit `--repo` / `--sample-shape` parameters over hidden filename/path inference.
- When customer-facing logs display tensor shapes, print plain tuple text rather than `torch.Size(...)`; if batch is fixed to 1, hide the batch dimension by default.
- When the deployment target is the v2.5 chip, do not treat software `dequantize()` as part of a deployable path; if a test reconstructs float modules from a quantized bundle, label it clearly as a software-side compile smoke rather than true chip-executable quantized deployment.
- When adding built-in compatibility for legacy SpikingJelly `clock_driven` neurons, cover both `IFNode` and `LIFNode`, and probe the legacy import path defensively so upstream removal of `clock_driven` does not break normal `activation_based` lowering.
- When a compatibility import only needs one known optional module, prefer a direct `try/except ImportError` over introducing a generic optional-import helper.
- When optional legacy compatibility is only needed if an import succeeds, gate both the helper function definitions and the registry entries under that import-success branch instead of leaving dead fallback symbols in module scope.
- When a type checker still flags attribute access on an optionally imported module inside a guarded branch, bind the needed attributes to local aliases inside that branch and use those aliases in nested functions and registry entries.
- When the user asks for the simplest implementation, reuse an existing model class if its deploy topology already matches the exported graph exactly; only define a separate deploy-only class when the export has materially different fused structure such as BN-folded biasful layers.
- When the user clarifies that an SNN deployment path should consume spikes at the first layer, do not keep image-style input quantization (`scale/zero_point`) in the compile path; prefer a 1-bit spike input assumption and only keep deployable integer parameter folding.
- When an SNN model's training/eval `forward()` still contains `out / self.T`, setting `T=1` alone does not remove the traced `truediv`; if the deploy path needs single-step compilation, rebind `forward` to `forward_once` directly instead of assuming FX will constant-fold the division away.
- When the user expects to inspect final compile artifacts, do not run the compile in a temporary directory only; write logs and backend export outputs to a stable repo-local `debug/` directory.
- When a customer-specific activation must lower to an exact integer-domain LUT but eager shape propagation still needs float tensors, use a float-forward shim module and register its lowering to `ANNNodeV25(LutReLU/LutCustom(...))` instead of dropping a real integer-output LUT module directly into the PyTorch forward path.
- When the user only needs the final end-to-end deployment smoke, remove intermediate metadata/config assertion tests and keep the file focused on the two final compile/export cases.
- When discussing an operator wrapper around a PyTorch API such as `torch.split`, distinguish the external API argument type from the wrapper's internal canonical storage type; describe the PyTorch input as `int | Sequence[int]` (or the documented `int | list[int]`) rather than accidentally restating the wrapper's normalized tuple form as the public call signature.
- When narrowing a lowering module to one supported operator family, do not keep unrelated unsupported siblings in that module's dispatch constants just to improve diagnostics; let unsupported operators fall back through the generic lowering error path unless there is a concrete supported-family reason to classify them specially.
- When shared helper functions are imported from a dedicated utility module and there is no local naming conflict, do not keep redundant private-style aliases like `as _get_*`; import them directly and keep call sites consistent across sibling lowering modules.
- When the user asks for a quickstart or GitHub-project-style doc, default to a concise README structure (`Workflow`, `Requirements`, `Install`, `Quick Start`, `Output`, `Notes`, `Next`) and avoid explanatory prose unless the user asks for depth.
- When compressing a quickstart into GitHub style, do not over-trim away deployment-critical content; still include how to prepare a deployable model, the main extension hook such as `register_neuron(...)`, the meaning of key compile parameters, and the user-controlled customization space.
- When the user explicitly says a document should be in Chinese, treat that as a full-document language override for that turn and convert all user-facing sections accordingly.
- When explaining configurable compile parameters, prefer scenario-based templates and semantic placeholder names over arbitrary example numbers.
- When a document is meant to be handed to users as a single standalone file, do not rely on “see other repo files” references to fill important gaps; inline the necessary explanation.
- When documenting custom-module lowering through `register_neuron(...)`, do not tell users to set `_is_leaf_module` by default; in the normal registration path the module type is already added to the tracer's custom leaf set.
- When a quickstart is for one customer deployment flow rather than general users, do not stop at generic API guidance; add the customer-specific fixed inputs, external dependencies, cut points, automatic registration steps, and recommended execution order from the actual application harness.
- When the user-facing quickstart is the only document to be delivered, integrate essential artifact-format details from secondary docs directly into it, especially exported file meanings and board/CPU handoff requirements.
